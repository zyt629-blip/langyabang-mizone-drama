# 灯虹动作与打戏设计

## 输入处理

1. 提取参与人物、能力差异、武器、地点、胜负结果、情绪目标和期望时长。
2. 调用 asset_search 查找用户已有角色、服装、场景、武器和道具资产。
3. 缺少关键创意方向时，调用 ask_user 提供两到四个互斥方案，例如写实压迫、快速凌厉、力量沉重和飘逸仙侠。

## 动作设计

1. 调用 read 读取 skill://denghong-action-director/references/action-workflow.md。
2. 调用 read 读取 skill://denghong-action-director/references/output-template.md，建立动作总览和镜头条目。
3. 根据任务采用武侠仙侠动作、人物调度、动态运镜、表演和视觉特效知识模块。
4. 将场景划分为建立、试探、升级、逆转、高潮和结果。
5. 每段动作拆为预备、发力、接触、反馈和收势。
6. 明确人物站位、运动方向、空间障碍、武器轨迹和受击后果。
7. 设计镜头时保持动作轴线和人物方向连续。
8. 特效只强化已经成立的动作和接触点。

## 视觉锚定

1. 缺少可用关键帧时，调用 image_generate 生成角色与场景关系清晰的动作关键帧。
2. 将参考图资产标识传入 image_asset_ids。
3. 记录返回的图片资产标识。
4. 批量生成视频前调用 ask_user 确认动作方案和关键帧方向。

## 视频生成

1. 为每个镜头编写主体动作、对手反应、运镜、环境反馈和结束状态。
2. 调用 video_generate，将对应关键帧资产标识传入 image_asset_id。
3. 按镜头顺序记录视频资产标识。
4. 检查动作因果、方向、武器、服装、人物身份和空间连续性。

## 交付

交付动作节拍表、镜头清单、关键帧资产、视频资产和连续性检查结论。


## 完整执行检查表

### 任务确认

- 读取用户原始请求并判断本技能是否适用。
- 识别主要目标、输出类型和使用场景。
- 区分已确认信息、参考信息和待推断信息。
- 不把示例误当成硬性要求。
- 不扩大用户没有提出的范围。
- 记录用户指定的风格、画幅和限制。
- 记录是否有图片、视频、脚本或资产输入。
- 缺少关键选择时再调用 ask_user。
- 选项必须互斥且会改变后续流程。
- 没有必要时不打断用户。

### 资料与资产

- 只读取当前模式需要的 reference。
- 先读取总指南，再读取质量检查。
- 需要案例时才读取 casebook。
- 通过 skill:// 路径读取资料。
- 有资产标识时优先使用标识。
- 没有标识时才调用 asset_search。
- 多个候选资产不能默选错误对象。
- 记录资产的角色、场景或道具用途。
- 记录可确认的视觉锚点。
- 记录不可确认的区域。
- 不凭空添加品牌、文字和身份。
- 不把推断内容写成已验证事实。

### 方案编排

- 先写目标，再写执行动作。
- 把复杂任务拆成可检查阶段。
- 每个阶段写清输入和输出。
- 每个阶段写清失败条件。
- 保持主体、空间和时间连续。
- 只让明确要求的变量变化。
- 将固定项和允许变化项分开。
- 不用泛泛的“保持一致”替代具体锚点。
- 对主要结果给出可验证标准。
- 高风险步骤设置一次重试上限。
- 不用重复生成掩盖理解错误。

### 工具调用

- 只使用允许的原生工具。
- 调用 read 前确认资源确实相关。
- 调用 image_generate 前准备完整 prompt。
- 调用 video_generate 前准备明确起始状态。
- 传入正确的图片资产标识。
- 使用用户要求的画幅和时长。
- 记录工具返回状态。
- 记录新生成的资产标识。
- 记录访问地址或可用结果。
- 工具失败时保留失败阶段信息。
- 不把计划或草稿当成生成结果。
- 不在一次调用中混入未经确认的多个方案。

### 质量与交付

- 检查输出类型是否正确。
- 检查主体数量、身份和关键结构。
- 检查空间、道具和材质连续性。
- 检查动作、视线和方向连续性。
- 检查画面是否裁切或畸变。
- 检查是否出现额外人物。
- 检查是否出现文字、水印或界面。
- 检查是否出现随机品牌或无关道具。
- 区分结构错误和轻微审美差异。
- 结构错误只重试一次。
- 第二次仍有轻微差异时如实说明。
- 交付摘要必须对应真实结果。
- 交付中列出资产标识和已知限制。
- 未成功返回时不声称完成。

## 任务边界

该 Agent 只在打斗、追逐、兵器对抗、施法、受击或明确高强度身体冲突成为主要任务时调用。普通对话、轻微走动、微表情和静态角色设定不要强行套用打戏流程。用户未说明胜负、时长或结尾状态时，可以先给出保守动作方案，并把不确定项列入确认问题。

## 动作设计字段

每个动作条目记录发起者、目标、起始站位、重心、脚步、手臂、武器或能力、接触点、对手反馈、环境反馈、结束姿态和下一动作入口。动作必须有动机和方向，避免“快速挥动、激烈碰撞”这类不可执行的空泛词。受击要说明身体部位、方向、力度、失衡方式和恢复时间。

## 节拍与镜头

先建立空间和对手关系，再进入试探、升级、逆转、高潮和结果。每段动作按预备、发力、接触、反馈、收势拆解；镜头优先保证动作可读性，再选择推拉摇移、跟拍或环绕。保持动作轴线、人物左右关系和武器朝向连续，镜头不因炫技遮住关键接触点。

## 资产与生成

调用 asset_search 时只检索用户已有角色、服装、场景、武器和道具。缺少关键视觉锚点时先用 image_generate 生成一张能看清站位和武器关系的关键帧，并记录资产标识。批量 video_generate 前，若存在多个动作方案或高成本生成，调用 ask_user 确认方案，而不是默认消耗资源。

## 安全和质量

避免无依据的肢体扭曲、瞬移、武器凭空变化、受击方向与镜头不一致和特效遮挡动作。检查身份、服装、道具、站位、轴线、时间顺序和结束状态。失败时只修正动作关系或镜头路径并重试一次，不把所有内容重写成另一场戏。
