# 灯虹剧本审核

## 适用边界

用于审核和诊断现有剧本。用户只提供创意并要求从零写故事时不调用本技能。未经用户要求不直接重写全文。

## 输入处理

1. 读取用户提供的剧本、梗概、分场或对白。
2. 明确作品类型、目标时长、集数、受众和已有角色设定。
3. 信息不完整时仍可开始审核，并在结论中标明无法验证的部分。

## 审核流程

1. 调用 read 读取 skill://denghong-script-review/references/review-guide.md。
2. 先复述故事主线、角色目标、主要阻碍和结果，确认理解没有偏差。
3. 检查因果链、信息铺垫、角色动机、人物关系和时空连续性。
4. 检查开场吸引力、冲突密度、转折位置、高潮强度和结尾推动力。
5. 检查对白是否符合身份、情境和人物关系，删除只为解释背景的生硬台词。
6. 检查场景、动作和特效是否能被清晰视觉化。
7. 将问题按严重程度排序，每个问题提供定位、影响和修改方向。
8. 调用 read 读取 skill://denghong-script-review/references/output-template.md，并按固定结构组织结果。

## 输出结构

- 故事理解摘要
- 严重问题
- 重要问题
- 可优化问题
- 人物与对白检查
- 节奏与结构检查
- 视觉执行风险
- 建议修改顺序
- 总体结论

所有判断必须引用用户文本中的具体情节或台词作为依据。没有发现的问题不强行制造。


## 完整执行检查表

### 任务确认

- 读取用户原始请求并判断本技能是否适用。
- 识别主要目标、输出类型和使用场景。
- 区分已确认信息、参考信息和待推断信息。
- 不把示例误当成硬性要求。
- 不扩大用户没有提出的范围。
- 记录用户指定的风格、画幅和限制。
- 记录是否有图片、视频、脚本或资产输入。
- 缺少关键选择时再调用 ask_user。
- 选项必须互斥且会改变后续流程。
- 没有必要时不打断用户。

### 资料与资产

- 只读取当前模式需要的 reference。
- 先读取总指南，再读取质量检查。
- 需要案例时才读取 casebook。
- 通过 skill:// 路径读取资料。
- 有资产标识时优先使用标识。
- 没有标识时才调用 asset_search。
- 多个候选资产不能默选错误对象。
- 记录资产的角色、场景或道具用途。
- 记录可确认的视觉锚点。
- 记录不可确认的区域。
- 不凭空添加品牌、文字和身份。
- 不把推断内容写成已验证事实。

### 方案编排

- 先写目标，再写执行动作。
- 把复杂任务拆成可检查阶段。
- 每个阶段写清输入和输出。
- 每个阶段写清失败条件。
- 保持主体、空间和时间连续。
- 只让明确要求的变量变化。
- 将固定项和允许变化项分开。
- 不用泛泛的“保持一致”替代具体锚点。
- 对主要结果给出可验证标准。
- 高风险步骤设置一次重试上限。
- 不用重复生成掩盖理解错误。

### 工具调用

- 只使用允许的原生工具。
- 调用 read 前确认资源确实相关。
- 调用 image_generate 前准备完整 prompt。
- 调用 video_generate 前准备明确起始状态。
- 传入正确的图片资产标识。
- 使用用户要求的画幅和时长。
- 记录工具返回状态。
- 记录新生成的资产标识。
- 记录访问地址或可用结果。
- 工具失败时保留失败阶段信息。
- 不把计划或草稿当成生成结果。
- 不在一次调用中混入未经确认的多个方案。

### 质量与交付

- 检查输出类型是否正确。
- 检查主体数量、身份和关键结构。
- 检查空间、道具和材质连续性。
- 检查动作、视线和方向连续性。
- 检查画面是否裁切或畸变。
- 检查是否出现额外人物。
- 检查是否出现文字、水印或界面。
- 检查是否出现随机品牌或无关道具。
- 区分结构错误和轻微审美差异。
- 结构错误只重试一次。
- 第二次仍有轻微差异时如实说明。
- 交付摘要必须对应真实结果。
- 交付中列出资产标识和已知限制。
- 未成功返回时不声称完成。

## 审核准备

先区分输入是完整剧本、分场提纲、单场片段、人物小传还是对白片段。完整剧本可以做全量审核；片段只能对可见范围下结论。记录用户指定的类型、平台、时长、集数和受众；没有这些信息时不臆测市场规则，而是注明审核假设。原文中的人名、场次、时间和台词是证据，不用记忆替换。

## 问题分级

致命问题包括因果断裂、人物目标互相矛盾、关键事件缺失、结局无法由前文成立和无法拍摄的核心场面；重要问题包括冲突启动过晚、转折缺乏铺垫、人物关系不清、重复场景和对白信息堆叠；可优化问题包括语气、节奏、镜头可视化和局部措辞。每项问题都写定位、证据、影响和可执行修改方向。

## 检查顺序

先复述主线和角色目标，再检查因果链和信息分配，再检查人物动机与关系，再检查节奏、开场、转折、高潮和结尾，最后检查对白、场景、动作、特效和生成可执行性。不要先润色句子再发现主线错误。用户只要求找问题时，不直接替用户重写全文。

## 修改建议

建议必须能落到场次、段落、角色或台词。可以给出删减、提前、延后、补铺垫、改变目标、重写冲突动作等方向，但不擅自添加新的支线、人物或结局。若存在多种改法，给出优先方案与取舍，不堆列十个同义建议。

## 交付与边界

交付顺序固定为理解摘要、优先级问题、人物对白、结构节奏、视觉执行、修改顺序和总体结论。引用原文时保持短而准确；无法验证的内容标为待确认。只有用户明确要求“直接改写”时才进入改写任务，否则保持审核性质。
